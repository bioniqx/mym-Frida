## Findings

### [BLOCKER] CONSTRAINED_OPCODES omits the get_var_ref_check/put_var_ref_check adjacency — permuted builds silently miscompile lexical closure-variable references
- Location: tools/protect/opcode_permute.py:30-77 (CONSTRAINED_OPCODES set)
- Issue: In the fork at the pinned commit, quickjs.c:33879 sets `get_op = OP_get_var_ref_check;` (closure variable with `is_lexical`, the `can_opt_put_ref_value` path of `OP_scope_make_ref` resolution) and passes it to `optimize_scope_make_ref`, which at quickjs.c:33379 emits `bc_buf[pos] = get_op + 1;` — the emitted opcode is the enum successor of `get_var_ref_check`, which must therefore be `OP_put_var_ref_check`. The canonical header encodes this: `DEF(get_var_ref_check, …)` / `DEF(put_var_ref_check, …) /* must come after get_var_ref_check */` (quickjs-opcode.h:174-175 at cd41bdbf). Neither `"get_var_ref_check"` nor `"put_var_ref_check"` is in CONSTRAINED_OPCODES, and both live in the shuffleable region (before the temp block, before the `#if SHORT_OPCODES` positional hold), so the tool may separate them.
- Why it matters: Verified empirically against the pinned header: with seed `deadbeefcafe01234567fedcba9876543` the pair lands at slots 118 and 4 (canonical 100/101); with a second seed, 152 and 5. On any such build, `get_op + 1` writes an unrelated opcode into the final bytecode whenever a compiled script references a captured `let`/`const` closure variable through this optimization (e.g. `function f(){ let n = 0; return () => { n = n + 1; }; }`) — silent miscompilation, i.e. wrong behavior or a VM crash inside the hardened agent, not a build failure. All of the slice's stated gates pass anyway (`make` exit 0; roundtrip on sample_agent.js, which never hits this path), and Steps 13-14 only check the bijection and the 13 starter-list names, so nothing in the plan catches it. Every other arithmetic dependency I re-derived from the pinned quickjs.c is correctly held (loc/arg/var_ref triples, check triples, with_* family, if_false/if_true/goto plus the `op ^= OP_if_true ^ OP_if_false` XOR trick, dec/inc/post_dec/post_inc, push_const/fclosure, define_method pair, call/tail_call pairs, get_var_undef family, nop/OP_TEMP_START boundary, SHORT region by position) — this is the single gap.
- Recommended fix: Add `"get_var_ref_check"` and `"put_var_ref_check"` to CONSTRAINED_OPCODES (holding both by name preserves their canonical adjacency and order; `put_var_ref_check_init` and `get_loc_checkthis` are referenced only by name — CASE labels and direct `dbuf_putc` — and need no constraint). Regenerate the permuted header, and re-run the plan's Steps 13-16 gates on the rebuilt fork. Extend the guardrail so this class of gap cannot recur silently: after `generate_permutation`, assert that every canonically adjacent pair consumed by a `get_op + 1`-style rewrite stays adjacent (at minimum the pairs in CONSTRAINED_OPCODES), failing the tool loudly otherwise.
